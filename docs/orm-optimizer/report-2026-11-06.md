## Finding details

### 1. missing-limit - `api/src/features/officials-registry/uploadDirectoryController.js:34` (High, Static only, access layer: raw-pg)

- **What the code does:** Executes `SELECT * FROM third_level_official_masterlist` without any `WHERE` clause and without a `LIMIT`.
- **Plan evidence:** Static only (remote database guard prevented query execution).
- **Why it matters:** As the official masterlist grows, this query forces PostgreSQL to perform a complete sequential table scan and stream every single column and row across the network to Node.js, increasing memory pressure and latency.
- **Suggested fix (not applied):** If pre-checking existing records during directory upload, project only identity fields (`SELECT "TLOid", email FROM third_level_official_masterlist WHERE email = ANY($1)`) or paginate with `LIMIT` and `OFFSET`.
- **Other sites in this group:** None.

### 2. query-in-loop - `api/src/features/official-profiling/repositories/tloAccomplishmentRepository.js:64` (High, Static only, access layer: raw-pg)

- **What the code does:** Awaits `SELECT id FROM third_level_officials_accomplishments WHERE id = $1` sequentially inside an `Array.map` or `for...of` loop for each submitted accomplishment.
- **Plan evidence:** Static only.
- **Why it matters:** Incurs N distinct network round-trips to the database on every profile save. Latency scales linearly with the number of accomplishments.
- **Suggested fix (not applied):** Fetch all existing IDs in a single query before the loop:
  ```sql
  SELECT id FROM third_level_officials_accomplishments WHERE id = ANY($1::int[]) AND tlo_id = $2
  ```
  and group/check against an in-memory `Set`.
- **Other sites in this group:** None.

### 3. query-in-loop - `api/src/features/officials-registry/uploadDirectoryController.js:246` (High, Static only, access layer: raw-pg)

- **What the code does:** Loops through directory rows and awaits `SELECT index_number FROM notable_achievements WHERE index_number = $1` individually.
- **Plan evidence:** Static only.
- **Why it matters:** Uploading an Excel file with hundreds of rows produces hundreds of sequential round trips, stalling the HTTP request.
- **Suggested fix (not applied):** Extract all `index_number` values from the spreadsheet first, execute one query `SELECT index_number FROM notable_achievements WHERE index_number = ANY($1::text[])`, and separate inserts from updates in memory.
- **Other sites in this group:** None.

### 4. select-all - `api/src/features/officials-registry/uploadDirectoryController.js:34` (Medium, Static only, access layer: raw-pg)

- **What the code does:** Uses `SELECT *` on the masterlist table during directory parsing.
- **Plan evidence:** Static only.
- **Why it matters:** Transmits wide columns, binary clearance references, and profile document fields that are completely unused by the upload validation routine.
- **Suggested fix (not applied):** Specify only the required fields: `SELECT "TLOid", email, status FROM third_level_official_masterlist`.
- **Other sites in this group:** None.

### 8. pool-no-max - `api/src/config/db.js:9` (Medium, Static only, access layer: raw-pg)

- **What the code does:** Instantiates `new pg.Pool(...)` with `connectionString` and `connectionTimeoutMillis` but without `max`.
- **Plan evidence:** Static only (configuration).
- **Why it matters:** Defaults to `pg` default of 10 connections. When scaling multiple PM2 cluster processes or Node instances, uncontrolled connection growth can exhaust database `max_connections`.
- **Suggested fix (not applied):** Explicitly declare pool constraints:
  ```javascript
  const pool = new pg.Pool({
    connectionString: process.env.DATABASE_URL,
    max: parseInt(process.env.DB_POOL_MAX || '10', 10),
    idleTimeoutMillis: 30000,
    connectionTimeoutMillis: 10000,
  });
  ```
- **Other sites in this group:** None.

### 9. write-in-loop - `api/src/features/official-profiling/repositories/tloAccomplishmentRepository.js:53` (Medium, Static only, access layer: raw-pg)

- **What the code does:** Iterates over accomplishment rows and awaits `UPDATE` and `INSERT` statements per item.
- **Plan evidence:** Static only (write operation; cannot be explained by SELECT analysis).
- **Why it matters:** Increases transaction duration and hold-time on locks when officials have large accomplishment portfolios.
- **Suggested fix (not applied):** Batch upserts using `UNNEST`:
  ```sql
  INSERT INTO third_level_officials_accomplishments (tlo_id, title, date)
  SELECT $1, * FROM UNNEST($2::text[], $3::date[])
  ```
- **Other sites in this group:** lines 72, 81.
